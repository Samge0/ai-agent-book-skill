# Patterns & Techniques — AI Agent Book

> Concrete design patterns, algorithms, and techniques extracted from "Deep Understanding of AI Agents" by Li Bojie.

---

## ReAct Loop (Reasoning + Acting)

**When to use**: Any agent that needs to interleave thinking and tool-calling.
**How**: Thought → Action → Observation → Thought (repeat until done). The LLM generates a reasoning trace before each tool call, then reads the observation to decide the next step.
**Trade-offs**: Transparent and debuggable, but verbose. Each step is an LLM call — latency and cost scale with steps. Minimize unnecessary reasoning on simple actions.

---

## KV Cache-Friendly Context Design (3 Commandments)

**When to use**: Any production agent making repeated LLM calls in a session.
**How**:
1. **Suffix-friendly** — put changing content at the end (tool results, recent turns), keep static content at the front (system prompt, tool definitions).
2. **Minimal-edit** — when updating context, change as few tokens as possible; append rather than rewrite.
3. **Explicit-cache** — use cache_control breakpoints on static prefixes to get explicit cache hits.
**Trade-offs**: Constrains prompt design freedom. But cache hits reduce latency 5-10x and cost ~10x. Always prefer cache-friendly structure.

## Agent Skills (Progressive Disclosure)

**When to use**: An agent has many capabilities but loading all instructions at once would consume too many context tokens.
**How**: Define each capability as a separate SKILL.md with a trigger-based description. The agent loads only the skill that matches the current task — skills are loaded on-demand, not all at once.
**Trade-offs**: Skill selection accuracy depends on the description field. Poorly-written descriptions cause missed triggers or false activations.

## Proposer-Reviewer Pattern

**When to use**: Tasks where a single-pass output is error-prone (code generation, document writing, translation).
**How**: One LLM call generates the output (proposer); a second LLM call reviews it against criteria (reviewer); the proposer revises based on feedback. Iterate until the reviewer approves or max iterations reached.
**Trade-offs**: 2x-3x the cost of single-pass. But catches errors that single-pass misses. Use for high-stakes outputs only.

## Three-Tier Safeguard (Code Execution Security)

**When to use**: Any agent that can execute code (coding agents, data analysis agents).
**How**:
1. **Tier 1 — Natural language rules**: Tell the model in the system prompt what's forbidden (e.g., "never run rm -rf /").
2. **Tier 2 — Checklist**: A pre-execution checklist the agent must self-verify before running code.
3. **Tier 3 — Server-side gate**: A sandbox/permission layer that physically blocks dangerous operations regardless of what the model tries.
**Trade-offs**: Tier 1 is free but unreliable; Tier 3 is reliable but expensive to build. Use all three layers — defense in depth.

## Context Compression Strategies

**When to use**: When conversation history exceeds the context window or degrades performance.
**How**: Choose based on the type of information:
- **Excerpt**: Keep verbatim quotes of critical facts (legal, code).
- **Summary**: Condense each completed sub-task into a 1-2 sentence summary.
- **Distillation**: Use a smaller model to compress old context into a compact representation.
- **Fixed template**: Replace repeated boilerplate with a fixed reference.
- **Selective**: Drop entire tool-call outputs that are no longer needed.
- **Extraction**: Pull out only the structured data (JSON, tables) and discard prose.
**Trade-offs**: Aggressive compression loses detail; conservative compression wastes context. Monitor accuracy degradation as you compress.

## Contextual Retrieval (RAG Enhancement)

**When to use**: Standard chunk-based RAG returns irrelevant or ambiguous results.
**How**: Before embedding, prepend each chunk with a brief context summary (generated by an LLM) explaining what the chunk is about and where it fits in the document. This disambiguates similar chunks.
**Trade-offs**: Requires an LLM pass over all chunks during indexing (one-time cost). Improves retrieval precision significantly.

## Agentic RAG

**When to use**: When a single retrieval pass is insufficient — the answer requires multi-hop reasoning or iterative search.
**How**: The agent decides when to retrieve, what query to use, and whether the results are sufficient. It can reformulate queries, retrieve multiple times, and cross-reference sources — turning retrieval from a one-shot call into a reasoning loop.
**Trade-offs**: More LLM calls per query. But handles complex questions that static RAG cannot.

## Two-Tier Memory Architecture

**When to use**: Building a persistent memory system for a long-running agent.
**How**: Store raw interaction logs in a vector database (Tier 1 — retrieval by similarity). Simultaneously maintain a structured knowledge base of distilled facts/preferences (Tier 2 — retrieval by lookup). New information is stored in Tier 1 immediately, then periodically consolidated into Tier 2.
**Trade-offs**: Two storage systems to maintain. But Tier 2 provides fast, accurate lookups while Tier 1 preserves full history.

## Model Swap Experiment (Evaluation)

**When to use**: Diagnosing which component (model, prompt, tool) is causing agent failures.
**How**: Swap one component at a time (e.g., replace GPT-4 with Claude, keep everything else identical) and measure the change in success rate. This isolates the marginal contribution of each component.
**Trade-offs**: Requires a reproducible evaluation harness. But it's the only way to know if a problem is model-bound or architecture-bound.

## LLM-as-Judge Evaluation

**When to use**: Evaluating agent outputs that are hard to score with rules (open-ended tasks, creative work).
**How**: Use a strong LLM (preferably a different model than the agent) to score outputs against rubrics. Provide explicit criteria, reference examples, and require structured scoring (not just "good/bad").
**Trade-offs**: Judge model has its own biases. Use pairwise comparison (which is better, A or B?) for more reliable results than absolute scoring.

## Ablation Infrastructure

**When to use**: Understanding which parts of your agent architecture contribute to performance.
**How**: Systematically disable components (memory, RAG, tools, specific prompts) and measure the success rate delta. Build a matrix of component → impact.
**Trade-offs**: Time-consuming (N components × M test cases). But reveals which components are load-bearing and which are dead weight.

## Pass@k vs Pass^k (Evaluation Sampling)

**When to use**: Evaluating agents on tasks with stochastic outputs.
**How**:
- **Pass@k**: Probability that at least 1 of k independent attempts succeeds. Measures single-attempt capability.
- **Pass^k**: Probability that ALL k attempts succeed. Measures consistency/reliability.
**Trade-offs**: Pass@k overestimates real-world performance (you usually get 1 try). Pass^k is stricter but more realistic for production. Report both.

## SFT Memorizes, RL Generalizes

**When to use**: Choosing between SFT and RL for model post-training.
**How**: SFT (Supervised Fine-Tuning) teaches the model to reproduce specific patterns — it memorizes. RL (Reinforcement Learning) teaches the model to optimize outcomes — it generalizes to unseen situations.
**Trade-offs**: SFT is cheaper and faster but overfits to the training distribution. RL is expensive and unstable but produces more robust, generalizable behavior. Use SFT for format/style alignment, RL for capability improvement.

## Mode-Seeking vs Mass-Covering (RL)

**When to use**: Choosing RL optimization mode for diversity vs quality.
**How**:
- **Mode-seeking** (low temperature in RL): The model converges to the single highest-reward strategy. Good for tasks with one clear best answer.
- **Mass-covering** (high temperature): The model maintains diverse strategies. Good for creative tasks or when you want exploration.
**Trade-offs**: Mode-seeking gives higher peak performance but brittle solutions. Mass-covering gives robustness but lower average reward.

## Externalized Learning (3 Products)

**When to use**: Building an agent that learns from experience.
**How**: When an agent encounters a failure or new insight, it externalizes the learning into one of three products:
1. **KB entry**: A new knowledge-base record (factual learning).
2. **Code tool**: A reusable function/script (procedural learning).
3. **Skill document**: A SKILL.md with trigger + steps (methodological learning).
**Trade-offs**: Requires deciding which type of learning each experience produces. But externalization is what makes learning persistent and reusable across sessions.

## Event-Driven Asynchronous Agent

**When to use**: Agents that need to respond to external triggers (webhooks, timers, messages) without blocking.
**How**: The agent runs a main loop but registers event handlers. When an event fires, it's queued and processed asynchronously. The agent can handle multiple concurrent tasks with a shared context.
**Trade-offs**: More complex architecture than synchronous agents. But enables real-time responsiveness and concurrent task handling.

---

## Proactive Tool Discovery

**When to use**: Environments where the tool set changes dynamically (MCP servers added/removed, new APIs available).
**How**: The agent periodically scans available tools, reads their descriptions, and decides which ones to load into context. Tools not in the current context cannot be called — so discovery is a prerequisite for using new capabilities.
**Trade-offs**: Discovery consumes context tokens. Balance between discovering all available tools and keeping context lean.
